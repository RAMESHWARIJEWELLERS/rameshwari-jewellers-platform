Conflict 3 — Resolution

Five proposed permanent identifiers, tested against the approved architecture. Four are unnecessary.
This revises my earlier recommendation

In the Development Blueprint I recommended approving all five. Applying your rules 3–5 — prefer existing structures, no new permanent object without a clear requirement, no redundant representations — that recommendation does not survive. One identifier is genuinely required. Four are not.

Decision table

rj_page_section

Required?YES
Type proposedCustom post type, private, show_ui true, REST true
Why requiredThe approved UI/UX Blueprint specifies frontend visual editing of Hero, About, Testimonials and Footer bands. Those bands need editable content that is not a Page, not theme markup, and not builder storage — because all three are lost on a theme change or builder removal, which the locked business rule forbids.
Can existing structure handle it?Partially, and badly. An options group could store the bands as JSON. That satisfies portability but loses three things the approved architecture already relies on elsewhere: post revisions (no undo on a mis-edit), scheduling (no festival or wedding-season band set in advance), and the media library's own picker UI per band. It would also mean the visual-edit layer writes to options for bands and to posts for everything else — two write paths where the architecture specifies one.
AlternativeOptions group rj_sections. Workable. Meaningfully worse.
Migration costNow: zero. Later, if bands start in options: a migration script plus re-entry of any scheduling. Small but real.
RecommendationCreate it — and absorb hero into it. See below.
Owner decision required?Yes. This is the one identifier that should become permanent.

rj_hero

Required?NO — as a separate type
Type proposedCustom post type
Why proposedHero slides need an image, copy, a CTA and a schedule, surviving theme changes.
Can existing structure handle it?Yes — rj_page_section is the same thing. A hero slide is an editable presentation band with an image, a heading, a sub-line and a CTA. That is the exact shape of a page section. Two post types for roughly nine total records across the whole site is a redundant representation of one concept, which your rule 5 forbids.
Alternativerj_page_section with section_key = hero_1, hero_2, hero_3. Scheduling, revisions, media picker and ordering all come free, identically. The maximum-three rule is enforced in the UI on the hero keys.
Migration costZero now. Merging two post types later would be a content migration.
RecommendationDo not create. Hero becomes a section key.
Owner decision required?Yes — confirm the merge is acceptable.

rj_reel_type

Required?NO
Type proposedFlat taxonomy on reels
Why proposedFiltering the reel feed by Styling, Craftsmanship, Bridal, Store Tour, Customer.
Can existing structure handle it?Yes, twice over. rj_tag is already registered on reels and is already the taxonomy for free keywords. rj_occasion is also already registered on reels and already carries Bridal and Festive. A third reel taxonomy overlaps both.
Honest noteFiltered reel browsing is not in any approved requirement. It is a refinement I proposed. By your rule 4 it does not clear the bar for a permanent object.
Alternativerj_tag terms, with the reel screen offering the five as suggested tags. If a curated filter row is later wanted, it reads a fixed list of tag slugs from the display settings group — no schema change.
Migration costAdding the taxonomy later is cheap: register it, then bulk-assign from the existing tags. No data loss either way.
RecommendationDo not create. Revisit if the reel library passes ~200 and tag-based filtering proves inadequate.
Owner decision required?No. Reversible later at low cost.

rj_location

Required?NO
Type proposedHierarchical taxonomy on showrooms
Why proposedStructured local-SEO markup and a home for a future third branch.
Can existing structure handle it?Yes, fully. The approved showroom meta registry already carries _rj_city, _rj_state, _rj_pincode, _rj_address, _rj_lat and _rj_lng. Local-business structured data is generated from those fields directly — a taxonomy term adds nothing the markup needs.
Argument against creating itA taxonomy would generate archive URLs such as /location/jhotwara/. With two branches, each archive lists exactly one showroom and duplicates that showroom's own page. That is thin duplicate content competing with the page you actually want ranking — an SEO liability, not an asset.
AlternativeThe existing meta fields. A third branch is a third showroom post; nothing needs to change.
Migration costAdding it later costs nothing — terms are derived from meta already present.
RecommendationDo not create. Reconsider at five or more branches across multiple cities, where archives stop being duplicates.
Owner decision required?No.

rj_customer_segment

Required?NO — as a taxonomy
Type proposedFlat taxonomy on the user object
Why the capability is requiredThe approved Notification Architecture routes bridal collection announcements to a Bridal Interest audience. Segments are an approved concept; the storage mechanism is what is in question.
Can existing structure handle it?Yes, and better. User meta with one row per segment — key _rj_segment, one row per value — is directly queryable by the notification audience resolver on an indexed key/value pair.
Argument against the taxonomyTaxonomies on the user object are not first-class in WordPress: no built-in admin UI, term counts are unreliable for non-post objects, and several REST and export behaviours assume post objects. It would mean building a custom management screen to replicate what a meta field gives for free, on a mechanism WordPress supports less well. This weakens rather than strengthens portability and future API compatibility.
AlternativeMulti-row user meta _rj_segment, added to the approved meta registry §9.5. Values: bridal_interest, silver_buyer, high_intent, dormant, staff_contact. Private, never public, excluded from REST.
Migration costZero now. Meta to taxonomy later, if ever needed, is a short one-way script.
RecommendationDo not create the taxonomy. Add one user meta key instead.
Owner decision required?Yes — this adds a key to the approved meta registry, which is itself a locked document.

One thing to weigh against this recommendation

Being conservative now means four capabilities arrive as conventions rather than as structure — suggested tags instead of a reel taxonomy, address fields instead of location terms. Conventions drift where schema does not. The mitigation is that each of the four is a cheap, one-script addition later, and each has a stated trigger for revisiting. That trade is the right one only because the triggers are written down; if they are not honoured, the conventions quietly decay.
