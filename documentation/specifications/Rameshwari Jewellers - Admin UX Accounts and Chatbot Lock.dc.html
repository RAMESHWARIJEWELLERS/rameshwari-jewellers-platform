Final locked wording — password reset

Password reset uses WordPress's own lost-password and reset flow: a single-use, time-limited, hashed reset key mailed to the account's verified address, redeemed once to set a new password, invalidated on use and on any subsequent request. The reset form is an RJ account-area template so the customer never sees wp-login.php, but the key generation, storage and verification are WordPress's — no parallel reset mechanism is built. Requests are rate limited (§6.4 registration and login limits apply), the response is identical whether or not the address is registered so the form cannot enumerate accounts, and every attempt and success is written to rj_login_log. A Google-only identity has no local password: the reset screen states that sign-in is managed by Google and offers no reset. A customer who wants both methods sets a password from the profile screen while authenticated, which is credential creation under an existing session rather than a second reset path.

Final locked wording — persistent session

A successful login establishes a normal WordPress authentication cookie, and the customer stays signed in across pages and visits until something ends it. Nothing asks them to log in again to browse. The session ends on explicit logout, on a password change or reset, on administrative or all-device revocation, on WordPress's own authentication invalidation, or at cookie expiry — WordPress's standard two-day life, extended to fourteen days when the customer chooses "remember me". No authentication token is ever written to localStorage or sessionStorage, and no permanent token is minted. Logout is nonce-protected (Technical Blueprint §10.2) and destroys the session token server-side, not only the cookie. Regression test 2 already requires every auth flow to pass headless with no third-party cookie and no session storage, which this wording satisfies rather than amends.

Part 6 · Chatbot admin controls — and the one decision

The enable/disable flag fits rj_features at no architectural cost. The rest of the configuration does not fit anywhere clean, and I am not resolving that silently.

RESOLVED — Option A approved. rj_chatbot is a locked tenth options group; secrets live in server-side configuration, never in the group.

The locked schema fixes nine options groups. A chatbot needs a welcome message, a fallback message, knowledge-source toggles, capability toggles, a human-support message, provider credentials and privacy controls. Two candidate homes:

#OptionConsequence
AA tenth group, rj_chatbot — not autoloaded, manage_options to write, no REST read, credentials from configuration constantsFollows the rj_notifications precedent exactly: a subsystem with its own messages and its own provider credentials gets its own non-autoloaded group. Changes the locked count from nine to ten.
BReuse existing groups — flag in rj_features, messages in rj_display, credentials in rj_auth_providersKeeps the count at nine, but puts chatbot copy into an autoloaded public-read group and AI credentials into a group named for login providers. Both are misplacements that a future developer would have to work around.

Recommendation: A. The nine-group count is a description of the current schema, not a constraint the architecture depends on — unlike the post-type and taxonomy counts, an options group creates no term IDs, no URLs and no migration risk. B saves a number at the cost of storing credentials in a group whose name lies about its contents. Your call; nothing else in this pass depends on it.
