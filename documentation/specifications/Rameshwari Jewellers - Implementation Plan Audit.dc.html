2 · Critical findings

S-1 · Public writes cannot pass gate 1 — the security model has no public branch

Severity CRITICAL · Category SECURITY · Must fix before Stage 0: YES

The plan's §13 states the gate order and gate 1 without qualification:

"Every write passes four gates in this order." … "1 · Capability · Rest\Permissions · Admin · A specific capability with the object where relevant. Never a screen check standing in for a permission check."

Gate 2 then acknowledges that public writes exist:

"2 · Intent · Nonce on forms and AJAX, header nonce on REST, origin check on public writes."

The collision: Development Blueprint §11.3 documents two writes whose permission column reads Public — POST /rj/v1/leads and POST /rj/v1/notifications/subscribe. An unauthenticated visitor holds no capability of any kind. So for those two endpoints gate 1 is either unsatisfiable (the enquiry form is dead) or silently skipped (an engineer decides on their own what replaces it). The plan does not say which, and "never a screen check standing in for a permission check" gives no guidance for a request with no user.

Why it matters: lead capture is the revenue path. Every WhatsApp click writes a lead server-side before redirecting. An engineer implementing Stage 10 must invent the public-write authorization policy, and the two obvious inventions are both wrong — treating gate 1 as optional removes the architectural requirement to think about abuse, and requiring a capability breaks the form.

Aggravating detail: the anti-abuse controls that should constitute the public branch appear exactly once in the whole plan, inside Stage 10's deliverables — "honeypot, dwell time, rate limit, 30-minute dedupe" — described as features of the leads module rather than as a gate every public write must pass. Notification subscribe therefore inherits none of them by rule.

Exact correction wording

Replace the §13 preamble and gate 1 row with a two-branch model:

Every write passes four gates. Gate 1 has two branches, and which branch applies is a property of the endpoint, declared once in Rest\Permissions.

1a · Authenticated write — capability. A specific capability with the object where relevant. Never a screen check standing in for a permission check.

1b · Public write — endpoint authorization policy. There is no user, so there is no capability; the gate is instead the declared anti-abuse policy, and a public endpoint that does not declare one fails review. The policy is: origin check, honeypot, minimum dwell time, per-IP-hash and per-identifier rate limits, replay and duplicate suppression, non-enumerating responses, and no open redirect. Applies to every public write — currently POST leads and POST notifications/subscribe — not only to leads.

Affected stages: 10 (leads), 11 (REST), 19 (notification subscribe), 20 (chatbot handoff writes a lead), 21 (security hardening audit).

T-1 · The launch gate cites a 20-test registry that does not exist

Severity CRITICAL · Category TESTING · Must fix before Stage 0: YES

The plan asserts the figure three times, including as the final gate of the entire project:

"All 20 regression tests green." · "21 · Hardening, testing, launch ── gate: 20/20 regression; tested restore" · Read scope for Stage 21: "Dev §21, §24 · this plan §14 → '20/20 regression tests green'"

The collision: the cited source, Development Blueprint §24, is titled "Critical Regression Tests" and contains 15 numbered rows, not 20. The plan's own internal citations use that 15-row registry correctly — it refers to "Regression 15: a lead insert that throws still returns a valid WhatsApp URL" and "Regression 12: export, import to a clean installation", both of which match §24's numbering. So the plan simultaneously cites a 15-test registry and gates on 20 tests.

Where 20 came from: the Session 5 brief listed 20 mandatory regression tests. §24 codified 15 of them. The five that were never carried across are identifiable:

#In the owner's 20, absent from §24's 15Nearest existing coverage
aHero media resolvesPartially — §18 media audit covers missing media, but no test asserts a hero campaign's two crops resolve
bCategory images resolveSame — audited daily, not asserted by test
cCustomer data survives theme switch§24 test 11 covers business data; it does not name wishlist, views or login history
dUnicode / Hindi content remains intact§24 test 12 covers it inside host migration only, not as an independent test
eCSV export safe from formula injectionCovered by the security suite, but not as a numbered regression test

Why it matters: a gate that names a count with no registry behind it cannot be passed or failed honestly. At Stage 21 an engineer either counts 15 and declares 20/20 — which is a false claim — or invents five tests of their own. Both outcomes defeat the gate.

Exact correction wording

Two options; the first is better because the owner asked for 20.

Preferred. Add rows 16–20 to Development Blueprint §24 using the five items above, each with a suite and an assertion in §24's existing column format. Then the plan's "20/20" becomes true and the gate is falsifiable. This is a Development Blueprint edit, not a plan edit — and it is the only must-fix finding that touches a document other than the plan.

Alternative. If the five are genuinely covered elsewhere and the owner accepts 15, change all three occurrences to "15/15 regression tests green (Dev §24)" and record in §14 that the owner's other five are covered by the media audit and security suite rather than by numbered regression tests.

Affected stages: 21. Also §14's testing strategy and §16's read-scope table.

A-1 · Two incompatible stage-ordering rules

Severity HIGH, must-fix · Category ARCHITECTURE · Must fix before Stage 0: YES

§17 states the rule as strict predecessor ordering:

"Stage N can begin only after Stage N−1's verification gate passes."

§5 states something incompatible:

"First parallel opportunity — After Stage 6, stages 7, 8, 9, 10, 11 touch different aggregates and may run in parallel with enough people — though 9 needs 7's media pipeline."

The collision, precisely: under §17's rule Stage 9 may not begin until Stage 8's gate passes, even though §5 says Stage 9's only real prerequisite is Stage 7. And under §5's rule Stage 11 may begin as soon as Stage 6 passes, which §17 forbids. Neither rule is a superset of the other, so a team cannot follow both. Worse, the parenthetical "though 9 needs 7's media pipeline" shows the parallel set is not internally independent either — so "all five in parallel" is also wrong.

Why it matters: this is the sequencing contract for the whole build. A team that follows §17 serialises work that could be parallel and pays weeks for nothing. A team that follows §5 may start Stage 9 before the media pipeline exists and discover it mid-stage.

Exact correction wording
Replace the §17 line with: "Stage N may begin once every stage in its declared dependency list has passed its verification gate. Dependencies are listed per stage in §6 and drawn in §5; they are not implied by stage numbering."

Then, in §5, replace "stages 7, 8, 9, 10, 11 … may run in parallel" with the explicit dependency list, since the prose already contradicts itself: 7 ← 6 · 8 ← 6 · 9 ← 7 · 10 ← 6 · 11 ← 6. That preserves the parallelism the plan intends while making Stage 9's real prerequisite binding.

Affected stages: all, as the governing rule. Materially 7 through 11 and 12 through 16.

3 · High and medium findings

A-2 · "REST-backed service methods" contradicts the plan's own layer table

Severity HIGH · Category ARCHITECTURE · Must fix before Stage 0: NO — fix before Stage 12

The anti-pattern table in §3 reads:

"Admin duplicating repository logic — Screens call the same REST-backed service methods. A screen with its own query is a review rejection."

The intent is right and the second sentence is exactly the correct rule. But "REST-backed service methods" admits two readings, and they have very different consequences:

ReadingConsequenceVerdict
(a) Admin screens call the REST API over internal HTTPEvery admin save becomes a loopback request — authentication re-established per call, doubled latency, and it breaks on shared hosts that block loopback to themselvesWrong, and plausible enough that an engineer may build it
(b) Admin and REST both call one shared service layerOne implementation of each operation, two thin adapters over itCorrect, and what §2 already mandates

The plan's own layer table settles it against reading (a) — layer 8 Admin is listed as depending on layers 1–5, and REST is layer 7. An Admin→REST call would be a dependency on a lower-numbered-but-later layer, violating the one-directional rule the plan calls "that single constraint is what produces every portability property." So the phrase contradicts the architecture two sections earlier.

Exact correction wording
"Admin duplicating repository logic — Screens and REST controllers both call the same application services; neither calls the other, and no admin screen issues an internal HTTP request. A screen with its own query is a review rejection."

Affected stages: 11, 12. Also check: §17's Stage 12 gate says "No screen queries directly" — correct, and should be extended to "and no screen calls REST over HTTP."

HA-1 · Two host capabilities the plan depends on are not in its unknowns table

Severity MEDIUM · Category HOSTING · Must fix before Stage 0: NO — before Stage 15

Credit first, because it is deserved: the plan has a "Genuine unknowns — stated rather than assumed" table with five correctly-classified rows, and it handles WebP/AVIF and persistent object cache exactly as this audit would demand — naming the resolving stage and the degradation path. That is the right pattern. Two dependencies of equal weight are missing from it.

DependencyStatusWhat breaks, and why it is not merely a performance question
Outbound mail delivery (wp_mail)ASSUMEDPassword reset, account verification, and the sole required notification channel all depend on it. On InfinityFree, mail is commonly blocked or silently dropped. If it fails, every email account is permanently locked out — there is no second reset path by design, and the plan states so. Unlike WebP, there is no graceful degradation: the account system stops working.
Outbound HTTPS from PHPASSUMEDGoogle OAuth's token exchange is a server-to-server call, and so is any AI provider request. Free hosts frequently restrict outbound requests. The plan's rule "no outbound request on any front-end request" is a performance rule and does not establish that outbound requests are possible — which Google login and the chatbot both require.
Exact correction wording — add two rows to the unknowns table
Whether the host delivers outbound mail reliably — Stage 15, by sending a real reset to a real inbox before the auth work is gated. If mail is unreliable, email/password registration must not be enabled on that host: Google login and the catalogue still work, and the SMTP transport swap in the notification architecture is the remedy. This is a blocker for the account system, not a performance question.

Whether the host permits outbound HTTPS from PHP — Stage 15 for Google, Stage 20 for the chatbot. Both degrade to unavailable-and-not-rendered, which the architecture already supports; the catalogue is unaffected.

P-1 · Performance gates name numbers without a reproducible environment

Severity MEDIUM · Category PERFORMANCE · Must fix before Stage 0: NO — before Stage 14

The plan's targets are specific and, in one case, admirably concrete about conditions:

"LCP under 2.5 s, INP under 200 ms, CLS under 0.05 on a mid-range Android on 4G in Jaipur; JS under 20 KB and CSS under 45 KB gzipped; mega menu under 50 ms at 1,000 terms" · "Admin product list under 800 ms at 20,000 products"

Classified against the audit's four questions:

MetricA · Requirement?B · Test target?C · Reproducible as written?
JS 20 KB · CSS 45 KB gzippedYes — an architecture constraintYesYes. A build-step assertion, environment-independent
Mega menu 50 ms at 1,000 termsYesYesPartly — needs the cache state named (cold, warm, transient-only)
Query count under 40YesYesPartly — needs the page and the cache state named
Admin list 800 ms at 20,000No — a test targetYesNo. No seed fixture defined, no hardware baseline, no PHP version
LCP · INP · CLSNo — test targetsYesNo. "Mid-range Android" is not a device; no throttle profile, no cold/warm state

Why it matters, and why not to weaken the targets: the numbers are reasonable and should stay. The risk is the opposite of laxity — an unreproducible gate gets measured on whatever laptop is nearest, passes, and the real phone in Jaipur is never tested. D · Could a target create an unrealistic constraint? Only the 20,000-product figure, and the plan already disarms it by listing real launch volume as an unknown and calling the load test "cheap insurance."

Exact correction wording — add to §14 once
Reference environment. Field metrics are measured on a named reference device — a mid-tier Android of the class the shop's customers carry, recorded by model in the test log — throttled to 4G (roughly 9 Mbps down, 170 ms RTT) with a cold cache, three runs, median reported. Admin timings are measured against a seeded fixture of 20,000 products and 1,500 terms generated by the Stage 18 importer, on the target production host, with the object cache in the state that host actually provides. A target measured anywhere else is not a passed gate.

D-1 · "Nothing is added later" forbids a future the architecture reserves

Severity MEDIUM · Category DATABASE · Must fix before Stage 0: NO

"All eight tables are created by migration 001 in Stage 3; nothing is added later."

The first clause is right and valuable. The second is an absolute the architecture does not need and cannot honour: the locked specification reserves OTP login, webhook delivery and a future analytics decision, and the migration router exists precisely so numbered migrations can follow. As written, a conscientious engineer reading this would believe a ninth table is forbidden by architecture rather than simply unnecessary today.

Exact correction wording
"All eight tables are created by migration 001 in Stage 3. No further table is required by the current specification; the numbered migration router exists so that a future approved decision can add one without disturbing these eight."

D-2 · Rollback vocabulary is used for four different operations

Severity MEDIUM · Category DATA-INTEGRITY · Must fix before Stage 0: NO — before Stage 21

The two statements below are not contradictory, and I want to be precise about that — the plan is describing different things and is right about each:

"Migrations are reversible or additive-only, numbered, idempotent, run behind a lock" · "Migration 001 is reversible in staging. In production, take the pre-release backup first — dropping tables is the one genuinely destructive step in the whole plan."

The real problem is vocabulary, not logic. The word "rollback" is used across §15 for four operations with different risk profiles, and the reader must infer which is meant:

OperationReversesData riskExample in the plan
Code rollbackPlugin versionNone"Redeploy the previous plugin version"
Data rollbackWritten rowsBoundedImport ledger, 30-day window
Config rollbackA settingNone"the cleanest rollback in the plan — one boolean" (chatbot)
Cache rebuildNothing — regeneratesNone"Drop and rebuild" (product index)
RestoreThe databaseTotal, if absentStage 3 migration failure

Why it matters: turning a feature flag off is called a rollback in the same table as restoring a database. Under incident pressure that flattening is how someone reaches for the wrong instrument — or believes they have a rollback for Stage 3 when what they actually have is a backup they must have taken in advance.

Exact correction wording — add to the head of §15
Four distinct operations, named separately throughout this section. Code rollback redeploys the previous version and touches no data. Config rollback changes a setting and touches no data. Cache rebuild discards derived data and regenerates it — never a loss. Data rollback reverses written rows and exists only where a ledger records prior values: imports, within 30 days. Everything else requires restore from the pre-release backup, which is why that backup is mandatory rather than advisory. Stage 3 has no data rollback — only restore.
