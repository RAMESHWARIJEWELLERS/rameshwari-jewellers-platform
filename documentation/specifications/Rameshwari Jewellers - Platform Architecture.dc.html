1 · Business Architecture

1.1 What the platform is

A showroom catalogue on the internet. The customer browses, saves, and enquires. The sale closes on WhatsApp or in the shop, exactly as it does today. There is no cart checkout, no payment gateway, no shipping engine and no WooCommerce — because none of those match how gold is actually sold in Jaipur, where price moves daily and every piece is discussed before it is bought.

The platform's job is therefore narrow and measurable: make 300+ categories and thousands of pieces findable in Hindi and English, make every piece one tap from a WhatsApp conversation, and give the owner complete control of the catalogue without touching code.

1.4 The enquiry path

Every surface in the platform funnels to the same three-step path, and every step is recorded.

Step 1 · Discover
Category tree, mega menu, search, collection page, reel feed, showroom page.
Step 2 · Consider
Product detail with gallery, weight, purity, metal. Wishlist if logged in; recently viewed either way.
Step 3 · Enquire
WhatsApp with a pre-filled message carrying the product code — plus a lead row written server-side before the redirect.

The lead row is written before the WhatsApp handoff, not after, because the customer never comes back to confirm. A click that reaches WhatsApp but never converts is still a lead worth calling.

2.2 The category tree at scale

The taxonomy carries the business's real vocabulary and must reach 1000+ terms with unlimited nesting. Three design decisions make that safe.

Decision 1 — one hierarchical taxonomy, not five

JEWELLERY, METALS, WEDDING, FOR and OTHERS are top-level terms inside a single rj_category taxonomy, not five separate taxonomies. A single tree means one mega menu builder, one breadcrumb, one archive template, one import format, and the freedom to re-parent any branch without a data migration. Cross-cutting facets that are genuinely orthogonal — metal, purity, audience, occasion — are also exposed as flat filter taxonomies (2.4), so a product can be both Gold Jewellery → कर्णफूल → झुमका and filterable by 22K, Women, Bridal.

Decision 2 — ordering and visibility live in term meta, never in name prefixes

Term meta keyTypePurpose
_rj_orderINTSort position among siblings. Gaps of 10 on creation so a drag-drop insert rarely renumbers the whole set.
_rj_visible0 / 1Hide from menu and archives without deleting. Default 1 — the historic bug where categories vanished came from defaulting to 0 on terms created outside the UI.
_rj_featured0 / 1Promote into the featured strip and mega-menu highlight column.
_rj_name_hiTEXTDevanagari name — झुमका. The term's own name holds the English/transliterated label.
_rj_name_enTEXTEnglish label override where the term name is a transliteration.
_rj_image_idINTAttachment ID for the category card and mega-menu thumbnail.
_rj_icon_idINTOptional small mark for menu rows.
_rj_seo_titleTEXTTitle tag override.
_rj_seo_descTEXTMeta description.
_rj_seo_noindex0 / 1Keep thin intermediate branches out of the index.
_rj_menu_columnsINTMega-menu column count for top-level terms only.
_rj_depth_cacheINTDenormalised depth, rewritten on re-parent. Lets the menu query one level without recursion.
_rj_path_cacheTEXTDenormalised ancestor ID path, e.g. 4/19/77. Powers breadcrumbs and "all descendants" queries with one LIKE '4/19/%'.

Decision 3 — a rebuild job owns the caches

_rj_depth_cache and _rj_path_cache are derived, never hand-edited. They are rewritten inside the same transaction as any re-parent, and a full rebuild runs on demand from Tools and nightly via cron. If they are ever wrong the site still works — it simply falls back to get_ancestors() — so a stale cache degrades performance, never correctness.

Circular reference guard

Before any wp_update_term that changes parent, the candidate parent's ancestor path is checked for the term's own ID. A match is rejected with an admin error. Term 0 is the only legal root. This guard runs on the REST route, the admin form and the importer alike, because it lives in the model layer, not the form handler.

Integrity rules

  • Deleting a product soft-deletes to archived visibility; only an administrator can hard-delete, and doing so nulls object_id on its leads while keeping object_code.
  • Deleting a customer erases profile and wishlist rows but retains their leads with customer_id nulled — the business record survives the account.
  • Deleting a term is blocked while count > 0; the UI offers reassign-then-delete as one transaction.
  • Orphan sweep, weekly: wishlist and recent-view rows pointing at missing posts, queue rows pointing at missing users, term meta on missing terms.

2.9 Migration and versioning

Every schema change is a numbered migration file that is idempotent and runs inside the upgrade router keyed on rj_db_version. Migrations never run on the front-end request; they run on admin_init behind a lock, or via WP-CLI. A migration that fails logs, rolls its own transaction back, leaves the version number unchanged and shows a persistent admin notice — it does not retry silently on every page load.

3 · WordPress Architecture

3.1 The four layers

Each layer may only depend downward. A layer above can be replaced entirely without disturbing anything below it — that single constraint is what makes the platform survive theme and builder changes.

Layer 4 — Presentation · Theme, Elementor, Gutenberg, Spectra, Kadence. Fully replaceable. Holds zero data.
Layer 3 — Output · Shortcodes, blocks, Elementor widgets, dynamic tags, template parts. Thin adapters over Layer 2.
Layer 2 — Domain · Repositories, models, the WhatsApp engine, the notification bus, validation. Pure PHP, no output.
Layer 1 — Data · CPTs, taxonomies, meta, options, custom tables, REST. Registered by the core plugin. Permanent.

The theme-independence test: switch to Twenty Twenty-Five with every plugin but rj-core disabled. Every product, category, reel, collection, showroom, lead and customer must still be present, listed, editable in wp-admin and readable over REST. The site will look plain. It must not be broken. This test runs at the end of every phase in Section 14.

4.11 Import, export and rollback

Three-phase import

  1. Upload and map. CSV or JSON is parsed, columns mapped to fields, and the mapping saved as a reusable profile.
  2. Dry run. Every row is validated with the same validators the UI uses. The report lists creates, updates, skips and errors by row number. Nothing is written.
  3. Commit. Rows are written in batches of 100 behind a lock. Every created ID and every changed field's prior value is recorded against a rollback token.

Rollback

A token is valid for 30 days. Rolling back deletes created records and restores prior values for updated ones, in reverse order, in batches. Media imported during the run is left in the library — deleting it could remove a file another record has since adopted. The rollback itself is logged and is not itself reversible.

Exports are streamed row by row with a UTF-8 BOM so Excel opens Devanagari correctly, and every cell passes through the formula-injection escaper.

5 · Customer Architecture

5.1 Login is a convenience, never a gate

Every page, every product, every reel, every category and every WhatsApp button works signed out. 6.5 Digests

A jewellery shop publishes in bursts — twenty pieces from one photo shoot. Twenty emails would cost the shop its subscriber list. Product and reel events therefore default to a digest: events accumulate against a recipient and are sent as one message on a schedule (daily 19:00 IST by default, weekly optional). Immediate delivery is reserved for owner-facing operational events, where latency matters.

9.1 Token architecture

Three layers. Components never reference a raw value; they reference a component token, which references a semantic token, which references a primitive. Changing the brand gold is one edit at the primitive layer.

12 · Security Architecture

12.1 The four gates

Every write in the platform passes four gates in this order. No exceptions, no shortcuts, and the order matters — checking capability after sanitising wastes work on a request that was never allowed.

#GateImplementation
1Capabilitycurrent_user_can() with the specific capability and, where relevant, the object ID. Never is_admin(), which only reports which screen is loading.
2Nonce / intentwp_verify_nonce on forms and AJAX; X-WP-Nonce on REST. Public write routes carry a rotating nonce plus an origin check.
3SanitiseTyped sanitiser per field, defined once in the field registry. Nothing is read from $_GET, $_POST, $_REQUEST, $_SERVER or $_FILES outside a sanitising accessor.
4Escape on outputesc_html, esc_attr, esc_url, wp_kses_post at the point of echo, never earlier. Escaping at save time is how double-escaped Devanagari appears.

12.3 Circular category references

Three independent guards, because this failure corrupts the tree silently and is expensive to unpick:

  1. Model layer. Any parent change validates that the new parent is not the term itself nor any of its descendants, using _rj_path_cache with a live get_ancestors() fallback.
  2. UI layer. The drag-drop tree refuses the drop visually; invalid parents are absent from the parent dropdown.
  3. Sweep. The weekly integrity job walks every term to a depth limit of 20; anything exceeding it is a cycle, is logged, and is re-parented to root with an admin notice.

12.6 CSV injection

Every exported cell whose first character is =, +, -, @, tab or carriage return is prefixed with a single quote before writing. This applies to lead names and messages, customer names, product names and every free-text field — the attack vector is a customer typing a formula into an enquiry form and the owner opening the export in Excel. Exports also carry a UTF-8 BOM so Devanagari renders, and are streamed rather than buffered.

12.7 Hardening defaults

  • File editing disabled: DISALLOW_FILE_EDIT recommended in wp-config.php; the health check flags its absence.
  • XML-RPC left to the host's policy but flagged if enabled with no need.
  • Application passwords disabled for rj_customer.
  • Security headers set where the plugin controls the response: X-Content-Type-Options, Referrer-Policy, X-Frame-Options on account pages.
  • Content Security Policy is documented as a hosting-level recommendation, with the exact directive set needed for YouTube and Instagram embeds.
  • Sessions: default WordPress cookie handling; no custom session layer, which is a common source of vulnerability.

13.5 Write-path cost

  • View counts are incremented on shutdown after the response is flushed, batched in the object cache and written every 60 seconds — not one UPDATE per page view.
  • Denormalised counters (_rj_enquiry_count, _rj_count_deep) are recomputed on schedule, never on read.
  • The activity log writes one row with a small JSON diff; it never serialises whole objects.
  • The notification queue is written in one multi-row insert per event, not one insert per recipient.

14.1 Sequencing rationale

Categories come before products because a product cannot be filed correctly into a taxonomy that does not exist yet, and re-filing 500 products later is a day of manual work. WhatsApp comes before reels because it is the revenue path. Builder integration comes after the public site because widgets should wrap renderers that have already been proven in templates. Customers and notifications come last among features because neither is required to sell, and both add ongoing operational obligations.
