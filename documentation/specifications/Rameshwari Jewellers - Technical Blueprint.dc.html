1.9 Theme-change survival

MechanismEffect on a theme switch
Data in the pluginNothing is lost. Products, categories, reels, collections, showrooms, leads and customers are untouched.
Components in the pluginCards, menu, viewer, filters and the WhatsApp button render identically under the new theme.
Templates with a fallback chainA new theme with no overrides falls through to the plugin's defaults and works immediately.
Tokens as the contractThe new theme adopts the token sheet and the look travels with it.
Rewrites owned by the pluginURLs do not change, so nothing 404s and no search ranking is lost.
Switch-safety checklistThe eight-point check from the approved architecture, run in staging before and after.

What is lost on a theme switch, by design: header and footer arrangement, homepage section layout, and any builder-composed page. These are rebuild work measured in hours, and they are the price of being able to switch at all.

Product → CategoryMany-to-many. A product may sit in several leaves — a silver बिछिया belongs under Silver → पेर के आभूषण and under FOR → Women. One category is marked primary, and the primary drives the breadcrumb and the canonical URL.

4.3 Unlimited nesting at scale

MechanismEffect
Denormalised path and depthEach term caches its ancestor ID path and its depth. Breadcrumbs, "all descendants" queries and the menu read the cache instead of recursing.
Derived, never authoredCaches are rewritten inside the same transaction as any re-parent, plus a nightly rebuild. If stale, the system falls back to live ancestor lookup — slower, never wrong.
Sibling ordering with gapsOrder values are spaced, so inserting one term rarely renumbers a whole branch.
Deep counts on scheduleDescendant product counts are written hourly. Nothing counts live.
Depth ceilingTwenty levels. Not a business limit — a cycle detector. Anything deeper is a corrupted tree and is re-parented to root with a notice.
Cycle preventionThree independent guards: model, UI and weekly sweep.
Practical ceilingAround 5,000 terms, where the whole-tree payload stops fitting a single cache object and the menu moves to on-demand level loading. Designed for 1,500.

4.5 Bilingual and SEO fields

ConcernApproach
Two names, one termHindi and English are two fields on the same term. No translation plugin, so a category can never exist in one language and vanish in the other.
SlugsLatin transliteration. Devanagari slugs percent-encode into unreadable strings and break on some shared hosts.
SearchOne query matches Hindi, English, slug and product code. Requires utf8mb4 with a Unicode collation, verified at activation.
SEO per termTitle override, meta description, noindex flag. Thin intermediate branches are kept out of the index deliberately.
CanonicalA product's primary category determines its canonical path. Secondary categories link to it, never duplicate it.
Structured dataBreadcrumb markup generated from the cached ancestor path — the same source the visible breadcrumb uses, so they can never disagree.
Language markingDevanagari runs marked as Hindi in the markup, so assistive technology switches pronunciation and search engines read the language correctly.

6.2 Authentication layers

LayerUsed byMechanism
NonePublic readsNo credential. Rate limited and cached.
Cookie + nonceThe site's own front end and adminThe standard WordPress path. Origin checked on writes.
Application passwordsA future mobile app, a CRM, an ERPPer-integration credential, revocable independently, scoped by the user's capabilities. Disabled for the customer role.
Token exchangeReservedThe slot for a future first-party app login. Not built now; nothing in the design prevents it.

No custom session layer and no bespoke token scheme. Both are common sources of vulnerability, and WordPress already solves the problem.

Persistent session

A successful login establishes a normal WordPress authentication cookie, and the customer remains signed in across pages and subsequent visits. Nothing asks them to log in again to browse. The session ends on explicit logout, on a password change or reset, on administrative or all-device revocation, on WordPress's own authentication invalidation, or at cookie expiry — the standard two days, extended to fourteen with "remember me". No authentication token is ever written to localStorage or sessionStorage, and no permanent custom token is minted. Logout is nonce-protected and destroys the server-side session token, not merely the cookie. Public catalogue browsing never requires login.

6.3 Rules every route obeys

  • An explicit permission callback on every route. Public routes state it literally, so it is visible in review rather than absent.
  • Declared arguments with validation and sanitisation. No route reads request superglobals directly.
  • An explicit response schema. Fields are opt-in, so a new meta key never leaks publicly by accident.
  • Pagination on every collection, with a hard maximum page size. No route can be asked for everything.
  • Cache headers and an entity tag on public reads; the category tree is additionally cached server-side.
  • Consistent error shape: code, message, HTTP status, and a field map where validation failed.
  • Versioned namespace. A breaking change becomes rj/v2; rj/v1 keeps working.

No client-specific API will be written. Every future client is a consumer of the same contract, which is the only way to keep one of them from quietly becoming the reason a field cannot change.

7.2 Authentication providers

ProviderPhaseDesign note
Email + password5Core sign-on with double opt-in verification. Works with no external service.

Phone OTPFutureInterface, settings group and the verified-phone field already exist. Needs an SMS provider and a budget.
Magic linkFutureSame interface. The cheap alternative where SMS cost is prohibitive.

Password reset

Email and password accounts support the full cycle: login → forgot password → secure reset → login. It uses WordPress's native lost-password mechanism — a single-use, time-limited, hashed reset key mailed to the account's verified address, invalidated on use and on any subsequent request. Requests are rate limited, and the response is identical whether or not the address is registered, so the form cannot enumerate accounts. The form is presented in the RJ account area so the customer never sees wp-login.php, but key generation, storage and verification are WordPress's — no parallel reset mechanism is built. A Google-only identity has no local password and is offered no reset; Google manages Google credentials. A local password is created only from the profile screen under an existing session, never minted to satisfy a reset request.

Unavailable providers are not rendered. If every provider is unavailable the account area is hidden and the site is a pure catalogue — a supported operating state, not an error.

8 · Notification Architecture

8.1 Three separable parts

PartResponsibilityWhy separate
EventsDeclare that something happened, with a documented payload.Any plugin can subscribe without touching the notification system.
QueueExpand the audience, apply preferences, schedule, de-duplicate, throttle.All policy lives in one place, so a new channel inherits every rule for free.
DriversActually send.Adding Firebase later touches one class and one settings row.

Nothing is sent during the request that caused it. Publishing twenty products enqueues and returns; the worker drains the queue. A slow mail server can therefore never make the admin hang — which is the usual reason notification systems get switched off permanently.

10 · Security Architecture

10.1 The four gates

Every write passes four gates in this order. The order matters: checking capability after sanitising wastes work on a request that was never allowed.

#GateRule
1CapabilityA specific capability, with the object where relevant. Never a screen check standing in for a permission check.
2IntentNonce on forms and AJAX, header nonce on REST, origin check on public writes.
3SanitiseA typed sanitiser per field, defined once in the field registry. Nothing reads request superglobals outside a sanitising accessor.
4EscapeAt the point of output, never at save. Escaping early is how double-escaped Devanagari appears.

10.2 Threat coverage

ThreatControl
XSS, stored and reflectedRich text passes an allow-list filter; everything else is plain-text sanitised. Output is escaped even though input was sanitised — the importer and REST are separate entry points. Request URIs are never echoed.
CSRFNonces on every state-changing request including logout, wishlist toggles and visual-edit saves. Per-operation action strings, not one global nonce.
SQL injectionPrepared statements with placeholders everywhere. Table names from the database prefix, never from input. Dynamic sort and limit values checked against an allow-list before use.
Privilege escalationCapabilities granted only at activation and upgrade, from one map. No runtime capability addition. Role tampering by other plugins is detected by Health.
Broken access controlObject-level checks. A wishlist route verifies the row belongs to the caller; a lead route verifies the capability, not merely that someone is logged in.
Unsafe uploadDeclared type verified against actual file content, both against an allow-list. Vector images disabled. Filenames sanitised. Execution prevented in the plugin's upload folder on both Apache and IIS.
CSV injectionAny exported cell beginning with a formula character is prefixed so a spreadsheet treats it as text. Applies to every free-text field, because the attack vector is a customer typing a formula into an enquiry form.
Spam and bot abuseHoneypot, minimum form dwell time, nonce, origin check and rate limiting. No third-party CAPTCHA — it is a hosting and privacy dependency.
Circular categoriesThree independent guards: model validation, a UI that refuses the drop, and a weekly sweep with a depth ceiling.
Google login abuseState parameter and PKCE verified; provider subject ID matched before email; account linking requires an ownership confirmation; client secret read from a configuration constant, never returned by REST, never logged.
Customer account abuseCustomer role holds read only, admin access redirected, application passwords disabled, own-record-only REST access, author enumeration blocked.
Secret exposureCredentials read from configuration constants when present; masked in the UI, redacted in logs and exports, never in a REST response.
Unsafe executionNo dynamic evaluation, no shell execution, no variable include paths. Enforced by a static-analysis rule in the build check.
Debug leakageError display forced off in production; Health warns if it is on.

12 · Media Architecture

12.1 Storage strategy

DecisionDetail
One libraryEverything goes in the WordPress media library. No parallel upload directory, no custom file table. The library gives search, reuse, backup-plugin coverage and REST for free, and a custom store would forfeit all of it.
References are IDsEvery image is referenced by attachment ID, never by URL. Moving the site, changing the domain, or offloading to object storage then changes nothing in the database.
OrganisationYear and month folders, WordPress's own scheme. Filenames sanitised and prefixed with the product code where one exists, so the library is searchable by code.
VideoUploaded video lives in the library on paid hosting. On free hosting, uploaded video is discouraged in favour of provider embeds — a single 20 MB reel exhausts a free storage quota quickly. The reel model supports both, so this is a hosting choice, not an architecture change.
Offload readinessBecause references are IDs and URLs are generated, moving uploads to object storage later is a plugin install, not a migration.

13 · Import / Export Architecture

13.1 Three-phase import

PhaseStageWhat happens
1Upload and mapFile parsed, columns mapped to fields, mapping saved as a reusable profile. Nothing written.
2Dry runEvery row validated by the same validators the admin UI uses. Report lists creates, updates, skips and errors by row number. Nothing written.
3CommitBatches of 100 behind a lock. Every created ID and every changed field's prior value recorded against a rollback token.

No import ever writes without a dry run first. The report is the approval step, and it is the difference between a bad spreadsheet costing five minutes and costing a day.

13.3 Rollback

AspectRule
Token lifetime30 days, then the ledger entry is purged.
What reversesCreated records are deleted; updated records are restored to their recorded prior values, in reverse order, in batches.
What does notMedia imported during the run stays in the library — deleting it could remove a file another record has since adopted.
Conflict handlingA record changed by a human after the import is flagged rather than silently overwritten. The operator chooses per record.
ReversibilityA rollback is itself logged and is not reversible. Rolling back twice is not a recovery strategy; a backup is.
InterruptionBoth import and rollback are resumable. A timeout mid-batch leaves a consistent state and a resume point.

15 · Deployment Architecture

Hosting architecture is approved. This section covers how code and content move between environments, and how the business gets back up when something goes wrong.

15.1 Environments

EnvironmentPurposeRules
LocalDevelopmentDebug on, error display on, real cron off, mail intercepted rather than sent.
StagingReview and rehearsalA copy of production data, search engines blocked, outbound mail disabled, all notification drivers in test mode. Every theme switch, every migration and every import is rehearsed here first.
ProductionLiveDebug display off, file editing disabled, real cron, backups verified.

Staging is not optional. It is the environment the theme-switch checklist and the import dry runs are meant to be run in, and without it both become production experiments.

15.2 Deployment by host class

HostMethodConstraints
InfinityFreeFile transfer, manualNo command line, no version-control deployment. Releases are uploaded as a versioned plugin archive through the dashboard. Slowest path, and the reason paid hosting is recommended from Phase 4.

cPanel VPSGit deploymentFull control; command-line migrations; real cron.
Managed WordPressThe platform's own pipelineFile writes restricted outside uploads — already an architectural rule, so no adjustment is needed.

Release procedure, every host

  1. Backup taken and its restore verified.
  2. Release applied to staging; migrations run; smoke test passed.
  3. Maintenance mode on production, if the release carries a migration.
  4. Files deployed from the release tag on main; migration runner triggered; version number confirmed.
  5. Caches flushed; rewrite rules flushed if routes changed.
  6. Health endpoint checked clean.
  7. Maintenance mode off; smoke test repeated on production.

15.3 Migration between hosts

StepActionNote
1Full backup of files and databaseRestore verified before anything else begins.
2Provision the new hostMatch or exceed the PHP and database versions.
3Transfer files and import the databaseCharacter set preserved as four-byte Unicode, or Devanagari corrupts on import. Verified immediately by reading a Hindi category name.
4Update site and home addressesBecause media is referenced by ID and no absolute URLs are stored, there is no search-and-replace through serialised content — the single most common migration failure, designed out.
5Re-establish cron and cachingServer cron configured; object cache enabled if available.

15.4 Backup, recovery and versioning

ConcernPolicy
Database backupDaily, retained 30 days. Weekly copy retained 6 months.
File backupWeekly full plus daily uploads. Retained 30 days.
Off-site copyAt least one backup stored away from the host. A backup on the same server is not a backup.
Pre-release backupAutomatic before any deployment or migration.
Restore rehearsalQuarterly restore into staging. An untested backup is an assumption.
Recovery objectivesRecover within 4 hours; lose at most 24 hours of content. Leads, being the revenue record, are additionally exported weekly.

Code versioningGit from Stage 0, semantic version numbers on all four plugins and the theme, a tag per release, a changelog per release. Repository hosted on GitHub. Branching model: develop receives all work; develop merges to main at release time; release tags are placed on main only.
Schema versioningA stored schema version drives the migration router. Migrations are numbered, idempotent, run behind a lock, and never on a front-end request.
Content versioningPost revisions on every content type, plus the activity log for everything revisions do not cover — taxonomy, settings and relationships.

16.2 Dependencies

PhaseBlocked byWhy
1 Database0Nothing is written outside version control with no backup.
2 Catalogue1Products need their fields and the tree to exist first. Categories must precede products — refiling 500 pieces later is a day of manual work.
3 Theme2Templates need real content to be built against. A theme built on fake data hides every real edge case.
4 Elementor3Widgets wrap renderers that have already been proven in templates.
5 Customers2Wishlist needs products. Independent of the theme and of Elementor.
6 Notifications5Needs an audience to notify.
7 Optimisation3, 4Optimising before the surfaces exist is guesswork.

Phases 5 and 6 can run in parallel with 3 and 4 if two people are working, because customers and notifications touch no presentation code. That is the only parallelism the dependency graph permits.

16.4 Risk register

RiskLikelihoodMitigation
Free hosting cannot carry the catalogueHighBudget paid shared hosting from Phase 3. The architecture moves with no code change — a database dump and a DNS switch.
Taxonomy grows during the buildCertainPath-matched import re-runs without duplication. Expect three taxonomy loads, not one.
Photography lags the buildHighProducts draft without images and publish in bulk later. No placeholder or stock imagery is ever committed.
Owner time for content entryHighSpreadsheet import from records the shop already keeps, plus a 90-second mobile publish path.
Scope creep toward e-commerceMediumThe catalogue-only decision is locked. Adding checkout is a new project with its own architecture.
Devanagari corruption on a host moveMediumFour-byte Unicode verified at activation and daily, and as an explicit migration step.
Cron unreliable on shared hostingMediumEvery job idempotent, batched, resumable, and runnable manually. Overdue jobs reported.
WhatsApp Business API costMediumDeliberately last. The free link path carries the business indefinitely.
Developer turnoverMediumWordPress standards, no bespoke framework, documented hooks, and these three documents.
Elementor breaking changeLowDocumented APIs only, version check at load, and the shortcode floor underneath everything.
