0 · Architecture Conflicts

Conflict 1 — Combined category terms

AspectDetail
Existing decisionThe approved taxonomy (Architecture Appendix A) records झुमका and झूमर as two sibling terms; likewise लौंग / लूंग, जंजीर / सांकली, कड़ा / कड़ी, चुटकी / बिछिया.
ConflictSection 8 of this session's brief writes them as single slash-joined entries: झुमका/झूमर, लौंग/लूंग, जंजीर/सांकली, कड़ा/कड़ी, चुटकी/बिछिया.
Technical impactFive terms versus ten. It changes term IDs, slugs, URLs, the import file, product filing and the mega-menu row count. Deciding after products are filed means re-filing them by hand. A slash in a term name also produces an awkward slug and reads badly in a breadcrumb.
RecommendationKeep them as separate terms, as approved. Where the shop genuinely treats two words as one thing, put the second word in the term's alternate-name field so search matches both — that is what _rj_name_alt is for (§9). This gives one URL, one filing decision, and both words findable.
Blocked until decidedThe Stage 2 category import file only. Everything else proceeds.

Conflict 2 — RESOLVED (Free-First Audit)

AspectDetail
Existing decisionThirteen widgets and seven dynamic tags, approved in the WordPress Architecture and mapped section-by-section in the UI/UX Blueprint.
ConflictSection 12 lists twenty-one. Four of the additions duplicate approved widgets under a second name: Store Locator duplicates Showroom Grid; Featured Categories duplicates Category Grid with its featured filter; Product Card duplicates a single-item Product Grid; Reel Viewer is not a placeable widget — it is a modal the Reel Grid opens.
Technical impactTwo widgets that render the same component diverge. The owner then has two Showroom widgets with different settings and no way to know which one a page uses. Every duplicate also doubles the control surface to maintain and test.
RecommendationBuild seventeen: the approved thirteen plus four genuinely new ones — Wishlist Button, Customer Account, Hero, and Notification Signup. Drop the four duplicates; Store Locator and Featured Categories become preset configurations of the widgets that already exist, offered as saved presets rather than separate widgets. Section 12 is written this way, with the dropped four listed and explained.
Blocked until decidedStage 21 only.

Conflict 3 — RESOLVED (Session 5A.1)

AspectDetail
Original conflictTwo post types and three taxonomies were proposed in the Technical Blueprint and appeared in neither the CPT nor the taxonomy list of the Session 4 brief.
ValidationEach was tested against the approved architecture in Session 5A.1: is the capability required, and can an already-approved structure provide it?
Owner decisionCreate rj_page_section. Scheduled hero campaigns are an approved business requirement — start date, end date, active state, order, image, bilingual titles, description, CTA — and a post type is the correct container: scheduling and revisions are native, and the record set grows over time as campaigns accumulate.

Also rejectedThe rj_sections options group proposed as an alternative container. Hero storage is the post type.
Net schema changeOne post type. No new taxonomy, no new table. Eleven meta keys on the new post type — a consequence of the approved field list, registered in §9.6.

Module contract

interface Module {
    public static function id(): string;
    public static function requires(): array;   // module ids
    public function register( Container $c ): void;   // adds hooks only
}

Constructors do no work, so the container can build the graph without side effects. register() only adds hooks, which makes load order irrelevant and every module testable in isolation.

3.2 rameshwari-elementor

AspectBehaviour
DependencyCore plugin and Elementor, both active.
ActivationIf either is absent it registers nothing and shows a notice. It does not deactivate itself — Elementor may be temporarily disabled during maintenance, and self-deactivating would require the owner to remember to turn it back on.
Elementor absent at runtimeDetected on plugins_loaded; the plugin returns before touching a single Elementor class. No fatal, no notice spam, no editor breakage.
Elementor version changeA compatibility check at load disables individual widgets with a notice rather than crashing the editor.
RemovedElementor-composed pages fall back to the theme's page template. Product, category, reel, collection and showroom pages are unaffected — they were never Elementor templates.
Business dataNone. Widget settings are layout settings; deleting them loses an arrangement, never content.

3.3 rameshwari-tools

AspectBehaviour
DependencyCore plugin.
ContentsWP-CLI commands (import, export, rebuild indexes, rebuild paths, regenerate media, run a cron job, health), bulk media utilities, a query debug panel, fixture loaders for staging.
ProductionNot required. Recommended on hosts with a command line; irrelevant on those without, because every command has an admin-screen equivalent in core.
RemovedNothing is lost. This is the plugin's design constraint: if removing Tools breaks an operation, that operation belonged in core.

3.4 The rule all three obey

No optional plugin may register a post type, a taxonomy, a meta key, a table, a capability or a setting. Each is a consumer of core, never a producer. The test is run at the end of every stage: deactivate all three, and every product, category, reel, collection, showroom, lead and customer is still present, still editable and still readable over REST.

  • Direct file access blocked at the top of every file; a stub index in every directory.
  • Error display forced off in production; a generic message to the client, detail to the log.
  • Security headers set on responses the plugin controls.
