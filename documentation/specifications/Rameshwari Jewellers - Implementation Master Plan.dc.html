Implementation Master Plan

Twenty-two dependency-ordered stages, each with an explicit verification gate and a named read scope. The codebase is empty, which makes this simpler than it would otherwise be.
The Part 1 finding, stated plainly

There is no existing WordPress codebase. I listed the project tree rather than assuming: it contains twenty specification documents, the design-system bundle, and two runtime files belonging to the document viewer. No plugin, no theme, no inc/, no namespaces, no CPT or taxonomy registration, no REST routes, no admin screens, no templates, no Elementor or Gutenberg integration, no AJAX handlers, no repositories, no services, no migrations, no tests, no build tooling, no autoloader.

This is a greenfield build. The KEEP / EXTEND / REFACTOR / REPLACE / REMOVE classification your Part 1 asks for has nothing to classify — every file is CREATE. That is good news: there is no legacy conflicting with the locked architecture, so the "existing codebase conflicts" list at the end is empty for a verifiable reason rather than an optimistic one.

2 · Architecture layers

Sixteen layers. The dependency rule is one-directional: a layer may depend only on layers above it in this table. That single constraint is what produces every portability property the specification claims.

The five prohibitions, and the mechanism that prevents each

ProhibitionPrevented by
Domain depending on Elementor or the themeDomain is layer 3; both are layers 11 and 12. A review rejection, and detectable by static analysis on the namespace map
Business logic in widgets or shortcodesBoth call the layer-9 renderer with arguments. A widget holds settings; it never holds a rule
Business logic in templatesTemplates receive a prepared view-model, never a raw post plus meta lookups — which is also what makes a theme override safe for a non-developer
Chatbot reading random post metaThe knowledge layer has no access to get_post_meta; its only inputs are repository methods
Admin duplicating repository logicAdmin screens and REST controllers both call the same shared application/service layer. Neither calls the other, and no admin screen issues an internal HTTP request to the site's REST API. REST remains the external API transport boundary. A screen with its own query is a review rejection

3 · Proposed directory structure

Derived from the locked Development Blueprint §1 and §2.1 rather than from the generic example in your brief. Three deviations from that example, each for a reason: src/Repositories and src/Validation are folded into src/Domain/<Aggregate>/ because a model, its repository and its validator change together; src/Database is src/Data because it also holds post-type, taxonomy and options registration, not only tables; src/Security is not a directory because security is enforced inside every write path rather than delegated to one, with only its reusable primitives living in Support and Rest/Permissions.

The load-bearing rule: a theme template is never the source of truth for business data. Contact details, WhatsApp numbers, addresses and hours reach a template only through the five bridge functions, and a Tools scan flags any phone-number-shaped string typed into post content.

6 · Implementation stages

Twenty-two stages, ordered by technical dependency rather than by visible feature. Four deviations from your example order, each with a reason: the resolver merges into the category engine (its mappings are term meta, and splitting them means writing the tree twice); shortcodes get their own stage before Gutenberg and Elementor (they are the compatibility floor everything else falls back to); the theme comes before the builders (widgets wrap renderers already proven in templates); and the category import moves earlier, because the theme must be built against real content — a theme built on fake data hides every real edge case.

RuleConsequence
One renderer, six front doorsA bug is fixed once and output is identical everywhere. Six implementations would diverge within a month.
Resolution happens in the query layerNo builder ever resolves a Model B term. A native Gutenberg query loop pointed at a resolver term returns empty rather than erroring — an accepted limitation, since our own block, widget and shortcode all handle it.
Templates receive a view-modelNever a raw post plus meta lookups. This is what makes a theme override editable by someone who is not a developer.
Mega Menu is a theme componentPlugin owns the cached tree, the visibility filtering and the query; theme owns placement and skin. Elementor Free cannot build headers, and requiring Pro is forbidden.
Five bridge functionsrj_contact() · rj_whatsapp_url() · rj_render() · rj_menu_tree() · rj_is_active(). All guarded by function_exists, so a theme installed without the plugin renders a plain WordPress site rather than a stack of errors.
Assets conditionalRegistered globally on init, enqueued only where a component renders. Slider libraries load once per page regardless of instance count.

13 · Security plan

Every write passes four gates in this order. The order matters: checking capability after sanitising wastes work on a request that was never allowed.

Gate 1 has two declared branches, and which branch applies is a property of the endpoint, declared once in Rest\Permissions and reused by the REST controller and every other entry point. A public endpoint that declares no policy fails review. There is no "public capability" — granting a capability to guests is forbidden.

#GateLayerRule
1aCapability
AUTHENTICATED WRITE		Rest\Permissions · AdminA specific capability with the object where relevant. Never a screen check standing in for a permission check. Unchanged and not weakened by 1b.
1bEndpoint policy
PUBLIC WRITE		Rest\PermissionsThere is no logged-in user, so there is no capability to check. The gate is the endpoint's declared authorization and anti-abuse policy: origin validation · honeypot · minimum dwell time · per-IP-hash rate limit · per-identifier rate limit where an identifier exists · replay protection · duplicate suppression · non-enumerating responses · safe same-site redirect handling · request validation · field sanitisation · output escaping · logging. Declared per endpoint, not inherited from a service.

15 · Rollback strategy

Five distinct operations. The word "rollback" alone is never sufficient — the table below names which one applies. Under incident pressure, flattening these is how someone reaches for the wrong instrument.

OperationReversesDefinition
Code rollbackPlugin versionRedeploy the previous code version. Reverses no business data by itself.
Config rollbackA setting or feature flagChange a configuration value. Reverses no database history. Turning the chatbot off is this, and it is not equivalent to restoring a database.
Cache rebuildNothing — regeneratesDiscard a derived cache or index and regenerate it from source. Never a loss.
Data rollbackWritten business rowsReverse written data only where the architecture maintains a rollback ledger — the import system, within 30 days. Nowhere else.
RestoreThe databaseRestore from a verified backup, when the operation cannot be safely reversed by a ledger. Stage 3 has no data rollback; restore is its only recovery mechanism, which is why the pre-release backup is mandatory rather than advisory.

Genuine unknowns — stated rather than assumed

UnknownWhen it must be resolved, and by what
Whether the target host can generate WebP and AVIFStage 7, by inspection. The pipeline degrades to JPEG with a Health warning, so this is a performance question rather than a blocker.

Which AI provider, if the chatbot is ever enabledStage 20, and deliberately deferred. The adapter interface means the choice changes one class.
Whether the target host delivers outbound mail reliably ADDEDStage 15, before the account system is considered complete — send a real password-reset email to a real inbox and complete the reset. wp_mail delivery is never assumed. If unreliable: email/password registration must not be enabled on that host until a supported mail transport is configured; Google login may continue if its own dependencies hold; catalogue browsing is unaffected. This is a blocker for the account system, not a performance question — password reset has no second path by design, so undelivered mail locks an account out permanently.
Whether the host permits reliable outbound HTTPS from PHP ADDEDStage 15 for the Google OAuth server-to-server exchange, Stage 20 for AI provider calls. Working front-end HTTPS does not establish that server-side outbound HTTPS is permitted — free hosts commonly restrict it. Both degrade to unavailable-and-not-rendered, which the architecture already supports. Never a front-end page-render dependency.
Whether the host offers PHP 8.2 or newer and WordPress 6.5 or newer ADDEDStage 0, before the first deploy. The core plugin's floors are RJ_MIN_PHP = 8.2 and RJ_MIN_WP = 6.5; below either, the plugin deactivates with a notice. Check the live control panel, not the help pages — Hostinger's contradict themselves, and InfinityFree sets the PHP version itself.
